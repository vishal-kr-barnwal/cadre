# Cadre Refresh

## Cohesive commits and retained context

For v6/schema-2 state, each approved operation produces one immutable receipt under `.cadre/receipts/` and a temporary recovery journal under `.cadre/stage/operations/`. Apply returns `receipt` (or the receipt fields directly): `operationId`, `receiptHash`, `trailers`, and `status: commit_pending`. Include the promoted files and receipt in one agent-created Git commit with both exact returned trailers. Commit execution stays with the agent. Use `candidate_apply` with `request: {mode: "reconcile", projectRoot, operationId}` after committing; reconciliation verifies a unique reachable commit and committed artifacts and changes temporary state only. Never add a follow-up record-SHA commit. An operation reference is `op:<operationId>`, not a Git revision to pass directly to shell Git. Resolve it through receipt reconciliation before Git range commands.

Before any dependent delivery, resolve `commit_pending`. On interruption, inspect the persisted recovery journal and original approval; use `candidate_apply` with `request: {mode: "resume", projectRoot, operationId, approvalDigest}` to finish the already-approved promotion. Reconcile an existing commit before creating another. Any drift or ambiguous/forged receipt blocks continuation. Never replace an approved recovery journal or fabricate its approval.

Use the scheduler and validation in mutation results. Do not immediately request the same status again. For `context_read`, retain `retainedContextToken` only after a complete successful read. Pass it on later reads only while that text remains in context, with the same token across continuation pages. Clear it after compaction, context loss, expiration, or a fresh task. Keep `knownSources` only for compatibility. Default pages are 48 KiB, maximum 64 KiB. Section identity/content hashes allow reuse despite unrelated file changes; source freshness is checked independently. Required project instructions, full current spec/plan, applicable constraints, and repository instructions remain authoritative. Consume every page and require `contextReady`. An explicit full-source dependency fallback must be read completely and reassessed; do not silently omit guidance.

Serialized errors are bounded to 8 KiB. Use `diagnostic_read` with the returned diagnostic ID only when fuller evidence is needed; paginate it. Do not dump cache path lists into conversation. Build outputs belong in the runtime-returned owned `buildCachePath`, never an arbitrary `.cadre/.build-cache` directory.

Legacy SHA records and immutable v1–v5 templates remain evidence. Migrate through one approved refresh at a quiescent boundary before creating a v6 execution. Retain each existing execution's original contract and preserve approvals, completed nodes, findings, journals, and archived learning. The v6 commit instructions here replace legacy follow-up provenance commits described below.

## Memory contract

Preserve phase history and existing handoffs. For active versioned-memory tracks (v3–v6), keep the marked `cadre:memory` JSON block inside Pattern Seed synchronized with the proposed spec/plan revisions and exact approved pattern hashes. During a v1/v2 refresh, every nonterminal active track must explicitly stage a reseeded `learning.md`; omission, a blank seed, unresolved metadata, stale revisions, or stale pattern hashes blocks inspection and promotion. Every applicable pattern requires its safe `patterns/<slug>.md` path, SHA-256, and human-readable relevance/constraints; never invent or silently omit guidance. When a staged plan changes revisions, include the reassessed learning file in `expectedFiles`. Inspect `candidate_inspect.learning` and `memoryInputs` as well as `plans`; resolve invalid or stale memory before approval. Immediately before direct promotion, re-inspect and compare the complete approved digest, including unchanged memory inputs; changed inputs require reassessment and a corrected approval. Archive apply performs this check in the runtime. Completed and archived learning remains historical evidence, not a claim that old hashes describe current patterns.

When `upgradeRequired` is true, delivery mutations remain blocked until the approved refresh records the status-provided runtime/template targets. Upgrade active seed metadata and workflow instructions in the same staged, digest-bound envelope; keep legacy terminal history unchanged and do not fabricate old handoffs. Reach a quiescent worker boundary first. Blocking a node, verifying cleanup of already integrated work, inspecting/staging candidates, and rendering the validated derived index remain available for recovery. Do not perform new implementation or integrations to bypass the upgrade. Publish target versions only after the approved context files have been promoted, then run full validation. On interruption, continue the existing refresh journal rather than requesting a second approval for unchanged consequences.

## Legacy SHA refresh bookkeeping contract (not the v6 path)

Stage `project.json` with the target versions but preserve its existing `lastRefresh` and history until the artifact commit exists. Do not stage a new `lastRefresh` with a null commit. The pending operation belongs in `operations/refresh-<id>.json`; `project_status` with full detail and the operations directory identify it during recovery. Promote version metadata last, record every promoted file including `project.json` in artifactProgress, and verify all approved hashes before committing.

After the artifact commit, atomically write the completed journal with `refreshCommit` and `status/checkpoint: completed`. Set `project.lastRefresh` to `{refreshPath, commit}`; append `{action: "refresh", commit, refreshPath}` to project history and affected track history exactly once. These are deterministic consequences of the original approval. Completed operation hashes are checked against the artifact commit, so subsequent provenance bookkeeping or later approved context changes do not invalidate historical evidence. Keep the completed journal; remove only the matching stage after the record commit. No generated-runtime inspection is needed to discover these shapes.


## Approval policy v2 migration

Before delivery, resolve each `APPROVAL_MODE_MIGRATION_REQUIRED` warning by including an explicit Track-or-Autonomous choice and its consequences in this refresh proposal. Never infer the choice from the old spelling. Preserve legacy Governed and Phase choices and the Governed fallback for an absent mode.

At a quiescent worker boundary, stage `state.approvalModeMigration` as `{ executionId, approvalMode: "track" | "autonomous", approvedAt, refreshPath: "refreshes/refresh-<id>.md" }`. The existing refresh operation owns the inspected digest and exact path/hash manifest; the migration record points to that refresh without embedding its own digest. For an active execution, include its journal and implement operation in the same envelope: set both `approvalMode` to the selected mode and `approvalPolicyVersion` to `2`, preserving nodes, commits, timestamps, and graph identity. For a completed execution, leave the journal and `lastExecution` byte-for-byte unchanged; the migration record supplies the explicitly chosen effective mode for subsequent review or execution inheritance.

When Autonomous is selected, also create `state.autonomousReview` using the durable authority schema in the installed review skill: bind the original execution ID, approved specification commit, original `baseCommit`, migration approval time, empty findings, and `implementing` or `reviewing` according to lifecycle. Assess any existing review findings and carry their identities/attempt evidence forward instead of erasing them. Track selection does not authorize an automatic review loop. Preserve completed/archived track history; migrate only when a nonterminal track will continue or inherit legacy authority.

Include all changed context, active seed metadata, policy records, journals, and state in one staged refresh envelope. Promote target project versions last and verify the selected authority before resuming delivery. Recovery, blocking, and cleanup of proven integrated work remain available before the migration is complete. Never fabricate historical human verification or broaden an unchanged journal by merely changing the default.
