# Cadre Revert

For explicitly opted-in GitHub projects only, read `references/github-collaboration.md` before mutations. Its PR ownership, phase synchronization and checkpoint publication rules supplement this workflow. Otherwise follow the local workflow unchanged; do not invoke GitHub tools.

## Cohesive commits and retained context

Each approved operation produces one immutable receipt under `.cadre/receipts/` and a temporary recovery journal under `.cadre/stage/operations/`. Apply returns `receipt` (or the receipt fields directly): `operationId`, `receiptHash`, `trailers`, and `status: commit_pending`. Include the promoted files and receipt in one agent-created Git commit with both exact returned trailers. Commit execution stays with the agent. Use `candidate_apply` with `request: {mode: "reconcile", projectRoot, operationId}` after committing; reconciliation verifies a unique reachable commit and committed artifacts and changes temporary state only. Never add a follow-up record-SHA commit. An operation reference is `op:<operationId>`, not a Git revision to pass directly to shell Git. Resolve it through receipt reconciliation before Git range commands.

Before any dependent delivery, resolve `commit_pending`. On interruption, inspect the persisted recovery journal and original approval; use `candidate_apply` with `request: {mode: "resume", projectRoot, operationId, approvalDigest}` to finish the already-approved promotion. Reconcile an existing commit before creating another. Any drift or ambiguous/forged receipt blocks continuation. Never replace an approved recovery journal or fabricate its approval. Resume checks the approved unchanged-input fingerprints before further writes. `OPERATION_INPUT_DRIFT` preserves the pending operation; retain changed files and deliberately restore the approved inputs or obtain an exact repair approval. Never alter recovery hashes, delete the journal, or repeat product work to bypass this gate.

Use the scheduler and validation in mutation results. Do not immediately request the same status again. For `context_read`, retain `retainedContextToken` only after a complete successful read. Pass it on later reads only while that text remains in context, with the same scope, token and knowledge arguments across continuation pages. Do not add or change `knownSources` midway through a paginated read; changing those arguments invalidates its cursor. Clear it after compaction, context loss, expiration, or a fresh task. Default pages are 48 KiB, maximum 64 KiB. Section identity/content hashes allow reuse despite unrelated file changes; source freshness is checked independently. Required project instructions, full current spec/plan, applicable constraints, and repository instructions remain authoritative. Consume every page and require `contextReady`. An explicit full-source dependency fallback must be read completely and reassessed; do not silently omit guidance.

Serialized errors are bounded to 8 KiB. Use `diagnostic_read` with the returned diagnostic ID only when fuller evidence is needed; paginate it. Do not dump cache path lists into conversation. Build outputs belong in the runtime-returned owned `buildCachePath`, never an arbitrary `.cadre/.build-cache` directory.

Existing 3.9.0/3.9.1/3.9.2 projects using schema-2 state and template v5 continue without a version-only refresh. If status reports `PROJECT_UPGRADE_REQUIRED`, stop mutations: install Cadre 3.9.0, reconcile interrupted operations and perform its approved refresh to schema-2/v5 at a quiescent boundary, then install 4.0.0 and reload the client. Preserve approvals, historical journals, SHA references and archived learning; never edit version labels to bypass this gate.

Load `.cadre/workflow.md`, project/track state, spec, plan, learning, review/revision history, recorded task commits, Git history, working tree, and dependent tracks. Read every affected file and relevant later diff before proposing a revert.

At every required clarification or approval boundary, show a concise impact summary or focused diff. Inspect the active host policy before calling `workflow_elicit`: if the task context reports approval policy `never`, including Codex Full Access, skip the form and ask the same short question once in chat. Otherwise prefer `workflow_elicit`, using `clarification` for at most three questions and `approval` bound to the exact revert proposal checkpoint. Treat only an `approved` result as approval. If it returns `fallback_required`, or immediately returns `declined` while the task explicitly reports policy `never`, ask the same short question once in chat; the latter is policy rejection, not a human decline. Never request secrets or retry the form.

Call `project_status` first with `view: "implementation"` and `trackId` for active canonical work, otherwise `view: "track"`; use its embedded structured validation and do not repeat `state_validate` at command entry. Stop on invalid state. Candidate-only or drafting state has no approved implementation provenance and must return to track/revise. For `completed` or `archived`, keep the source immutable and propose a linked successor bug track containing the rollback; do not reverse Git or reopen/move the terminal track here.

Expected human decision count is one on the clean path. The exact revert proposal authorizes additive Git reversals, tests, plan/state/learning reconciliation, generated indexes, commits, and provenance bookkeeping when their content and consequences remain unchanged.

1. Resolve the exact task, phase, or track and its worker commits, task-to-phase merge commits, phase-to-canonical merge commits, and execution journal. Detect shared commits, later overlapping edits, active workers/worktrees, dirty changes, and dependent work.
2. For an eligible active track, build the exact additive revert proposal, call `candidate_stage_prepare` for `revert-<track-id>` with `expectedFiles` equal to every reconciliation artifact, and render exactly those files beneath the stage. Include `reverts/revert-<id>-baseline.json` in that manifest and write the returned `revertBaseline` JSON there before inspection. It fingerprints pre-existing product/policy edits and the index at the approved base. Retain those exact bytes through reversal and recovery; later stage preparation must not replace the original baseline.
3. Call `candidate_inspect` once for the staged reconciliation set. Supply one `planValidations` entry for every staged root or nested `plan.md`, using its exact candidate-relative path and post-revert track status; omit the list only when the candidate contains no plans. Present every plan result, the manifest, Git operations, expected diff, downstream reconciliation, verification, index, and commits as one authorization envelope bound to its digest. Never rewrite public history by default.
4. Call `template_get_many` for `track/revert-operation`, render the approved operation into `state.json.operation`, and persist it before any Git mutation. Record the target kind/ID, safe reverse commit order, base commit, expected reconciliation commit, approved manifest digest and path/hash entries, approval time, checkpoint, and applied revert commits. Resume a matching operation; never replace it.
5. Reach the authorized quiescent execution boundary before reverting. Use `git revert` to create additive reversal commits, using the correct mainline parent for an approved merge-commit revert. After each successful revert commit, record its SHA and advance the operation checkpoint. If a conflict has one unambiguous in-scope resolution that preserves the approved resulting semantics, resolve and verify it inside the envelope. If it introduces a material choice or changes the proposed result, stop and present one corrected proposal rather than accumulating per-file approval prompts.
6. Before promoting any staged file that replaces the temporary revert operation, atomically persist `reverts/revert-<id>.json` from that actual approved operation, with the recorded reversal SHAs and `reconciliationCommit: null`. Read the receipt back and verify its digest, approval time, original snapshot path, and reversal SHAs against the still-persisted operation. Stop if the receipt is missing or differs. Only then promote the approved staged Cadre files, verify their canonical hashes, reconcile plan checkboxes without erasing provenance, set the earliest affected task/phase back to pending or blocked, and mark dependent tracks for approved revision/reseed as needed. The final staged state restores implement ownership; the receipt now preserves the revert authorization through that transition.
7. Run relevant tests and verify the final candidate proposal. Apply using candidate_apply, commit `cadre(revert): reconcile <track-id>` with its operation receipt and exact trailers, then reconcile. Remove only the matching candidate stage. Do not turn these deterministic consequences into a second approval. Never fill a self-referential reconciliation SHA or create a follow-up record commit. On resume, never repeat reversal SHAs already recorded by the approved operation.

If exact commit provenance is missing or commits mix unrelated work, stop with a precise manual recovery plan.

## Group reversal and reconciliation

A task sharing a product commit cannot be reverted alone. Enumerate every task using that SHA, present the whole group and downstream effects, and obtain explicit approval for all of it. Include a staged reversal record with `sharedCommit` and exact `affectedTaskIds`, reset every affected task as approved, and retain the exact original journal snapshot. Candidate validation rejects silent sibling reversal.

After the authorized additive Git reversal commits, use `candidate_apply` prepare/apply with `workflow: "revert"` for the approved reconciliation manifest. Include the actual reversal receipt, original journal snapshot, restored execution bindings, plan, learning and dependency context. Make one reconciliation commit with the immutable operation receipt and exact trailers; reconcile it without filling a self-referential SHA or making a record-revert commit. Never repeat recorded reversal commits on recovery.

The pre-reversal authorization binds the `candidate_inspect` digest, exact authored reconciliation files, Git targets and resulting semantics. A pre-reversal `candidate_apply` preview is a structural check, not a token to apply after Git changes: its digest also binds HEAD and canonical state. After the approved reversal, prepare the final promotion from the same approved files plus the explicitly authorized reversal record with actual SHAs and approval fields. Verify that every authored file still matches the approved inspection, except those named bookkeeping consequences, and that runtime `stateChanges` preserve the approved execution ownership. Apply that post-reversal token under the original combined approval only when all consequences remain within that envelope. Changed product semantics, targets, artifacts or dependencies require a corrected proposal and approval. Do not apply a stale pre-reversal token or ask again solely because the authorized reversal advanced HEAD.

## Memory contract

Preserve phase history and existing handoffs. For active tracks, keep the marked `cadre:memory` JSON block inside Pattern Seed synchronized with the proposed spec/plan revisions and exact approved pattern hashes. Every applicable pattern requires its safe `patterns/<slug>.md` path, SHA-256, and human-readable relevance/constraints; never invent or silently omit guidance. When a staged plan changes revisions, include the reassessed learning file in `expectedFiles`. Inspect `candidate_inspect.learning` and `memoryInputs` as well as `plans`; resolve invalid or stale memory before approval. Immediately before direct promotion, re-inspect and compare the complete approved digest, including unchanged memory inputs; changed inputs require reassessment and a corrected approval. Archive apply performs this check in the runtime. Completed and archived learning remains historical evidence, not a claim that old hashes describe current patterns.

## Preparation safety and execution binding

Preparation is read-only outside the declared candidate stage. Never run `git revert` (including `--no-commit`), `git reset`, `git restore`, checkout, clean, stash, or index writes as a dry run in the target repository. A command described as a dry run can still destroy evidence. Inspect `git show`, `git diff`, status, and recorded commits to propose the reverse patch. If application must be tested, use an explicitly isolated disposable clone and retain all original dirty files; do not experiment in the delivery worktree. Before and after preparation verify unchanged HEAD, index, working tree, and hashes of uncommitted journals/learning. Host shell permission does not authorize a Cadre revert.

When temporarily replacing an implement operation with the approved revert operation, preserve `lastExecution: {executionId, journal, planRevision, graphDigest, headCommit, completedAt, approvalMode}` throughout the repair, copying those values from the persisted journal (including null head/completion values on an active run); include that exact proposed state in staging. After reconciliation restore the original implement operation, with the selected task pending as approved, before clearing the temporary revert. Preserve every handoff and original task SHA as evidence; workerHistory contains worker IDs, never commit SHAs. Never clear both execution references while a journal is in progress. Include state, execution journal, plan and reassessed learning in the single proposal. Do not change plan revisions or task descriptions merely to reset completion markers.

Candidate paths never include a leading `.cadre/`: use `state.json`, `plan.md`, `learning.md`, `executions/execution-<id>.json`, and `reverts/revert-<id>.md` for the owned track, or `tracks/<id>/...` for nested updates. Revert artifact IDs use lowercase letters, digits and hyphens: for target `T1.1`, use `reverts/revert-t1-1.md` and `reverts/revert-t1-1-execution-before.json`, while retaining `targetId: "T1.1"` in the evidence. Do not put uppercase node IDs or dots in artifact basenames. The stage already supplies the root. Use `candidate_inspect` to validate the full proposed overlay before asking for approval.

Stage the final post-reconciliation state, retaining the original implement operation, rather than a temporary revert operation containing unknown approval fields. After approval, materialize the temporary revert journal from the template with the actual digest/time before Git mutation, retaining the execution binding in lastExecution. The final staged state restores implement ownership. Do not put unresolved approval placeholders or a self-referential digest into approved candidate bytes.

`candidate_apply` prepare returns `stateChanges` for runtime-derived fields: apply each `set` or array `append` to the staged state (or canonical state when none was staged), then verify the reconstructed final state against its returned manifest hash. A changed state hash alone does not mean execution ownership was removed. Include these exact derived changes in the reviewable proposal; never inspect the installed runtime to reconstruct them.

## Durable reversal evidence

Before resetting node evidence, include the exact original execution journal as `reverts/revert-<id>-execution-before.json` in the inspected manifest. Preserve original verification, authorization, commit pointers, handoffs and all other nodes. Set the proposed journal checkpoint to `reverted:<target-id>`.

After Git reversal, persist the actual approved operation as `reverts/revert-<id>.json` before restoring implement ownership. Include its digest, approved artifact hashes, reversal SHAs and original snapshot path. Keep `reconciliationCommit` null; the immutable operation receipt supplies provenance without rewriting this evidence. A pending receipt uses resume/reconcile; never repeat a reversal or request another approval for unchanged consequences.

## Revert authority preservation

A phase completion or fast-forward HEAD reverses only its own commit delta; its `mergeCommit` field does not imply a Git merge object. Include every distinct task boundary in direct-main and fast-forward phase/track reversals. Collapse tasks into an actual phase merge only when they were introduced relative to its explicitly selected mainline parent. Tasks already in that parent still need their own reversal; never reverse a task again when the chosen merge reversal already covers it.

Receipt promotion requires the actual persisted approved revert operation, reachable additive reversal commits, its exact durable reversal record and original execution snapshot, and restored implement ownership matching the retained execution. Preserve authored commits, dependency/revision counters, review cycles and approval-policy metadata. Keep the complete original `autonomousReview` in authored state; the runtime derives the execution checkpoint while retaining any existing blocker. Never shorten `initialBaseCommit`, replace the originating authorization, reset findings/attempts, or substitute retry authority as a reversal consequence. State-only authority rewrites are rejected before promotion. A blocked loop still requires the separately approved refresh retry to continue.

Copy `candidate_inspect.files` into the persisted operation's complete `approvedArtifactHashes`, with exactly the paths in `approvedArtifacts`; there is no `manifest` field in that result. Every authored final artifact must retain its approved hash, including state and unrelated journal nodes. The only added artifact is the exact reversal record whose basename matches `originalExecutionPath` without `-execution-before`. Runtime-derived history/checkpoint fields are applied after these checks. Missing hashes, extra files or changed authored bytes require exact corrected approval; never mint replacement hashes from changed files under the old approval.

Set `repositoryBaselinePath` to the originally inspected baseline artifact in the temporary approved operation and its exact reversal record. Reconciliation permits those unchanged pre-existing edits while rejecting new product/policy changes; it never cleans, stashes or commits user files. A pending older reversal without this evidence retains its original clean-input contract; changed inputs require an exact repair approval. Clean review still verifies the final delivered product separately.

Git targets must belong to the named task, phase or track, including the explicitly approved whole shared group. Include every delivery boundary needed to reverse that scope, without reversing task commits a second time when an approved phase integration already covers them. Reset the affected nodes and dependency/phase consequences while retaining unrelated nodes, worker history, handoffs and the execution contract. Clear selected quiescent worker ownership (`workerId`, `branch`, `worktreePath`) for the new run, retaining the original worker ID in `workerHistory` and the exact before-snapshot. A commit from another task/phase cannot satisfy the target merely because it occurs in the same journal.

Record exactly one actual reversal SHA per approved target in the approved reverse order. Each target must have retained execution provenance. The runtime computes Git's rename-aware reversal result using an isolated temporary index, object directory, worktree and refs, preserving the delivery index, objects and history; ancestry or a commit message alone is insufficient. For merge targets, include `mainlineParents: {"<target SHA>": <parent number>}` in the pre-reversal operation and approval envelope. If preparation in a disposable clone discovers a conflict, include its exact approved result tree as `conflictResolutionTrees: {"<target SHA>": "<40-character tree SHA>"}`. The result may change only that target's paths and Git-verified later renames of those paths. An unforeseen resolution requires corrected exact approval before reconciliation. Empty, unrelated, missing, reordered or wrong-result reversals are rejected. Product or verification-policy drift after the last reversal also stops reconciliation; preserve those changes and the original evidence.

New pending reversals retain the original temporary operation and authored state in the ignored recovery journal, so resume revalidates approval hashes, Git proof and deterministic state even after candidate-stage loss. A valid older intent can retain that proof before further writes when its exact original state/stage remains available. Older partial intents missing original authority or approval hashes need an explicitly approved evidence repair; preserve the intent and receipt, never alter their hashes, erase history or repeat Git reversals to bypass this failure. Already committed replay stays zero-change after later delivery or archive.
